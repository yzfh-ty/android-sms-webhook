# eSIM 卡到期提醒与备注需求文档

日期：2026-10-30。基于当前 0.2.1 代码整理。

状态：已据此开发 0.3.0 首版。本文保留需求与设计建议的区分；当前实现和验证情况见[实现与验证记录](实现与验证记录.md)，使用方式见[开发版使用说明](开发版使用说明.md)。

## 1. 目标与已明确的要求

在现有短信转发工具中增加 eSIM 卡资料管理，帮助用户记录每张卡的用途与有效期，并在需要时提醒续期。

用户已明确要求：

1. 卡片信息由用户手动录入。
2. 支持填写、查看和修改备注。
3. 支持设置到期时间及提醒时间规则。
4. 每张卡分别保存到期时间、提醒规则和续期周期，互不影响。
5. 提供“已续期”按钮，按该卡设置的周期重新开始计算。
6. 点击“已续期”后必须先确认，确认后才更新。

这里的“卡”是用户维护的一条资料记录，不要求该 eSIM 已安装在当前手机中。首版不读取运营商套餐、不自动获取到期时间、不执行充值或安装/删除系统 eSIM。

## 3. 建议的首版范围

支持卡片新增、编辑、查看、删除，以及备注、到期状态、独立提醒设置和确认续期。概览显示已到期和即将到期数量，并可进入卡片列表。

以下为尚未由用户明确指定的建议：

| 项目 | 建议规则 |
| --- | --- |
| 提醒渠道 | 支持手机通知和现有企业微信机器人，按卡选择，可同时开启 |
| 默认渠道 | 手机通知；企业微信需用户主动选择并完成机器人配置 |
| “多久提醒”的含义 | 拆成“提前多久开始提醒”和“开始后多久重复提醒”，避免混淆 |
| 默认提前量 | 提前 1 天，用户可改为 0，即到期时才提醒 |
| 默认重复策略 | 仅提醒一次；可改为每隔 N 小时/天提醒 |
| 续期周期 | 用户按卡设置正整数天数或月数，不替用户猜测套餐周期 |
| 已过期卡片 | 允许录入，并按规则安排一次当前到期提醒 |

这些默认值只用于新建表单的初始展示。保存后每张卡独立持有配置，修改一张卡不会改变其他卡或后续新卡。

## 4. 每张卡的信息

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 卡片名称 | 是 | 如“香港保号卡”“旅行流量卡”；去除首尾空白后 1～50 字 |
| 运营商/套餐名称 | 否 | 自由填写，最多 100 字 |
| 号码/识别信息 | 否 | 手动填写手机号、卡号尾号等，最多 100 字；不要求提供完整 ICCID |
| 备注 | 否 | 多行文本，最多 2,000 字，支持中文、换行及表情 |
| 当前到期时间 | 是 | 选择日期和具体时间；表单显示计算使用的时区 |
| 续期周期数值及单位 | 是 | 正整数，单位为天或月；建议上限分别为 3,650 天、120 月 |
| 提醒开关 | 是 | 仅控制本卡的主动提醒，不隐藏到期状态 |
| 提前提醒量 | 开启提醒时必填 | 非负整数，单位为小时或天 |
| 重复提醒策略 | 开启提醒时必填 | “仅一次”或“每隔 N 小时/天”；N 必须大于 0 |
| 提醒渠道 | 开启提醒时必填 | 至少选择一个渠道 |

系统维护稳定的卡片 ID、创建/修改时间、上次续期时间、当前周期起点、规则版本和提醒进度。用户首次录入只需提供到期时间，不必反推套餐最初开通时间。

提示用户不要在备注中填写 eSIM 激活二维码、激活密钥或账户密码。备注默认仅保存在应用内，不自动发到群里。

## 5. 页面与交互

### 5.1 卡片列表

建议新增底部“卡片”入口，形成“概览 / 卡片 / 记录 / 设置 / 诊断”五个入口。

- 空列表显示“还没有卡片”和“添加卡片”。
- 每项显示名称、到期时间、剩余时间、提醒状态与备注摘要。
- 状态使用文字配合颜色：“正常”“即将到期”“已到期”。关闭提醒时另显示“提醒已关闭”。
- 默认按到期时间升序排列，最早到期的卡片在前；相同时间按创建时间稳定排序。
- 点击进入详情；列表中可提供“已续期”快捷按钮，但也必须经过相同的确认流程。
- 不同卡片可有相同名称，始终使用卡片 ID 定位记录；确认弹窗附带识别信息，减少混淆。

### 5.2 新增/编辑

表单按“卡片信息 / 到期与续期 / 提醒设置”分组，备注使用多行输入框。

保存前校验必填项、数值和时间范围，错误提示紧邻对应字段。提醒关闭时允许保留原提醒规则，但不产生通知。选择企微却未配置机器人时，引导完成配置或改用手机通知，不能显示为已启用企微提醒。

保存成功后刷新列表和调度。保存失败保留输入并显示原因。返回时若有未保存修改，提示“放弃修改 / 继续编辑”。

### 5.3 详情

显示完整资料、完整备注、到期状态、续期周期、提醒渠道、下次提醒时间及最近提醒结果。主要操作为“已续期”，次要操作为“编辑”；删除放在独立的次要菜单中并二次确认。

通知点击后进入对应卡片详情。目标卡片已删除时，进入卡片列表并提示“该卡片已删除”。手机通知中不直接提供跳过确认的续期操作。

按钮使用符合 Android 习惯的触摸区域，支持系统字体缩放；状态不能仅靠颜色表达。保存和续期提交中禁用重复点击并显示反馈。

## 6. “已续期”的计算与确认

### 6.1 建议计算规则

将用户所说的“从头开始”解释为：**以本次确认续期的时间为新起点，加上该卡保存的周期，得到新的到期时间**。

```text
新周期起点 = 本次确认续期时间
新到期时间 = 新周期起点 + 本卡续期周期
新首次提醒时间 = 新到期时间 - 本卡提前提醒量
```

例如：A 卡周期为 30 天，用户在 2026-10-30 10:00（Asia/Shanghai）确认续期，则新的到期时间为 2026-11-29 10:00。B 卡周期为 90 天时，A 卡的操作不会修改 B 卡。

提前续期、到期当天续期、过期后续期均按本次确认时间重新计算。提前续期可能使新到期时间早于原到期时间，弹窗应明确提示这一结果；首版不自动把周期累加到旧到期时间上。

按天计算使用该卡时区的日历天，保留当地时刻；按月使用日历月，不能用固定 30 天代替。月末不存在对应日期时取目标月最后一天。涉及夏令时缺失/重复时刻时采用统一的时间库规则，并在确认界面展示实际结果。

### 6.2 确认弹窗

示例：

```text
确认“香港保号卡”已续期？

当前到期：2026-11-02 10:00
续期周期：30 天
重新起算：本次确认时刻
预计新到期：2026-11-29 10:00
提前提醒：1 天
提醒方式：手机通知；仅一次
时区：Asia/Shanghai

确认后将重新开始本卡周期，并取消旧周期尚未发送的提醒。

[取消]  [确认已续期]
```

取消、返回或点击弹窗外部均不修改任何数据。确认时读取最新卡片数据与当前时间重新计算，最终结果通过成功提示和详情页展示；弹窗等待期间如果卡片已修改或被删除，应要求重新查看，不能用旧数据覆盖。

### 6.3 确认后的更新

在同一次数据库事务中更新周期起点、到期时间、上次续期时间和规则版本，并使旧周期未发送提醒失效。提交成功后取消旧调度、建立新调度、清理旧手机通知，再提示“已续期，新到期时间：……”。

续期不修改备注、名称、提醒偏好和其他卡片。未开启提醒的卡片续期后仍保持关闭。提交失败不能提示成功；重复提交同一次确认只生效一次。

已经送达的企微消息无法撤回；已交给网络请求的提醒也存在与续期并发的窗口，消息需标明对应到期时间，避免误认成新周期。

## 7. 提醒时间与状态规则

令 `D` 为到期时间，`L` 为提前量，`R = D - L` 为开始提醒时间：

| 条件 | 卡片状态 |
| --- | --- |
| 当前时间 < R | 正常 |
| R ≤ 当前时间 < D | 即将到期 |
| 当前时间 ≥ D | 已到期 |

关闭提醒只停止发送，仍按保存的提前量展示到期状态；提前量为 0 时，到期前不出现“即将到期”。界面显示具体剩余天/小时数，临近到期不因取整误报“已到期”。

建议提醒行为：

1. **仅一次**：本周期在 R 到达后提醒一次。如果录入、重启或恢复时已超过 R，尽快补发一次，并依据当前时间使用“即将到期”或“已到期”文案。
2. **重复提醒**：R 到达后首次提醒，此后按本卡间隔重复。到期后继续提醒，直到续期、关闭提醒或删除卡片。
3. **错过多个时段**：恢复时只补发一条当前提醒，不逐条补发历史时段；重复策略从本次提醒事件生成时间计算下一次机会，失败重试不生成新的提醒事件。
4. **重叠任务**：同一卡、同一规则版本最多一条未完成提醒事件；未完成时后续扫描只恢复原事件，避免离线期间堆积。
5. **修改规则**：修改到期时间、提前量、重复间隔、时区、渠道或提醒开关时递增规则版本，失效旧待发事件，按新规则计算。仅改名称或备注不重置已提醒标记，也不额外发送。
6. **删除**：删除记录时取消该卡调度、未发送事件及手机通知，不影响其他卡。已经发出的企微消息保留。

开启提醒时展示“下次提醒时间”；时间已过但尚未执行时显示“等待提醒”。渠道受阻时显示具体原因，不能把“已入队”当成“已送达”。

## 8. 提醒渠道建议

### 8.1 手机通知

使用独立的“eSIM 到期提醒”渠道，每张卡有独立通知标识，重复提醒更新本卡通知，不覆盖其他卡或投递故障通知。无网络也能执行本地提醒。

通知显示卡片名称、到期时间与到期状态；不默认显示备注、完整号码或其他识别资料。没有通知权限或渠道被禁用时，卡片仍可保存，界面显示“手机通知不可用”及设置入口，不能记为已提醒。

### 8.2 企业微信机器人

复用现有机器人配置、文本协议、加密凭据、共享限频和重试能力。首版不新增每卡一个机器人的路由功能；每卡仅选择是否使用当前机器人。

建议内容：

```text
eSIM 到期提醒
卡片：香港保号卡
状态：即将到期
到期时间：2026-11-02 10:00（Asia/Shanghai）
请续期后在应用内点击“已续期”并确认。
```

使用独立的 `esim_reminder` 来源标识，记录页可区分短信和卡片提醒。备注默认不外发。不同渠道分别保存执行结果，一处失败不重发另一处已完成通知。

卡片提醒开关与短信转发开关独立：暂停短信转发不能暂停卡片提醒，短信过滤规则也不作用于卡片提醒。现有按 `source != 'test'` 暂停任务的逻辑需要调整，否则新增卡片任务会被误暂停。

企微事件生成时保存目标快照。保存新机器人地址不自动改变已有待发事件的目的地；如用户明确选择切换目标，应先确认。已知的超时重复窗口仍然存在，不承诺企微端恰好收到一次。

## 9. 数据与实现建议

此节保留实现规划。首版已采用版本 3、新增两张表、规则版本校验及独立提醒任务；卡片时区固定为创建时手机时区，首版编辑界面暂不支持改时区。

建议 Room 版本从 2 升级至 3，新增：

| 数据 | 建议内容 |
| --- | --- |
| `esim_cards` | UUID、名称、可选资料、备注、到期时间戳、时区 ID、周期数值/单位、提醒开关、提前量、重复间隔、渠道选择、周期起点、上次续期时间、规则版本、创建/修改时间 |
| `esim_reminder_events` | 事件 ID、卡片 ID、规则版本、事件计划时间、下次重试时间、各渠道状态、发送结果及必要快照 |

唯一约束覆盖“卡片 ID + 规则版本 + 提醒事件标识”；发送前重新验证卡片存在、提醒开启且版本仍有效。到期状态由时间计算，不长期保存为容易过时的固定值。修改卡片后保留已完成事件用于最近结果展示，旧版未完成事件标记失效。

号码、备注等敏感资料复用现有加密能力；日志不输出备注、完整号码、机器人密钥或激活信息。迁移保留全部原有短信与机器人设置，不使用破坏性重建；新装和升级后卡片列表均为空，不从短信自动猜测卡片。

本地提醒扫描不设置网络约束，企微投递单独等待网络。数据库为真实状态，调度可根据持久化记录恢复；保存卡片后未能成功入队的缺口由启动及周期恢复扫描补齐。

后台建议复用 WorkManager，并增加应用打开、重启解锁、应用升级后的恢复扫描。手机时区变化不改变卡片保存的到期时刻与计算时区；更改卡片时区需在编辑界面预览结果。设备时间变化后应重新检查计划，去重记录不能因时间回拨清空。

提醒按“尽快执行”设计，不承诺精确到秒，首版不增加精确闹钟或常驻服务。系统后台限制、关机或强行停止可能延迟提醒；恢复后按本节及第 7 节规则补发。实际后台表现需真机验证。

## 10. 验收场景

| 场景 | 预期结果 |
| --- | --- |
| 新增 A、B 两张卡，设置不同日期、周期、提前量、重复间隔及渠道 | 重启应用后分别保留，互不覆盖 |
| 编辑 A 卡备注 | 正确保存多行中文和表情，不改变周期或触发额外提醒 |
| 输入空名称、0/负数周期、0 重复间隔或非法时间范围 | 对应字段提示错误，不能保存非法配置 |
| 提前量为 0 | 到期时开始提醒，之前不误显示即将到期 |
| “仅一次”策略经历多次扫描和进程重启 | 同一规则版本不重复创建首条提醒 |
| 重复策略跨过到期时间 | 提醒文案变为已到期，继续按本卡间隔提醒 |
| 点击“已续期”后取消 | 到期时间、提醒进度、备注均不变 |
| A 卡在 2026-10-30 10:00 确认 30 天续期 | 新到期为 2026-11-29 10:00；B 卡不变 |
| 提前续期使新到期早于旧到期 | 确认前清楚提示，取消不产生修改 |
| 1 月 31 日确认按月续期，或跨闰年 | 正确取目标月最后一天，非固定 30 天 |
| 连续点击确认或任务并发执行 | 同一次续期只提交一次，每次提醒事件不重复创建 |
| 确认弹窗打开期间卡片变化或被删除 | 不使用旧数据覆盖，提示重新查看 |
| 续期或改期时已有旧提醒排队 | 旧版本任务失效，新周期按新计划执行 |
| 手机通知失败、企微成功，或反之 | 分别显示渠道结果，不重发已完成渠道 |
| 无通知权限、禁用通知渠道、未配机器人 | 提供清晰提示，不虚报送达 |
| 断网时提醒 | 手机通知可用，企微按现有策略等待和重试 |
| 关机或停用很久后恢复 | 每卡最多补一条当前事件，不集中发送历史提醒 |
| 暂停短信转发 | 卡片提醒仍按独立开关执行 |
| 修改备注、关闭提醒、删除卡片 | 分别符合第 7 节的重置和取消规则 |
| 从数据库版本 2 升级 | 原短信和配置保留，卡片表正确创建 |

## 11. 开发前可调整的建议项

用户的核心要求见第 1 节，下列仍属于草案选择：

- 是否同时需要手机通知和企业微信通知，以及默认启用哪个渠道。
- “多久提醒”是否需要提前量与重复间隔两项；本文先同时设计，重复默认关闭。
- 续期是否只支持按天，还是同时支持日历月；本文建议两者都支持。
- 是否需要首版就提供续期历史或误操作撤销；本文首版仅显示上次续期时间，通过确认弹窗避免误操作。
